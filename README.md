# 铝厂余料转炉 · 再生料申报审核页

质检员在签发“最低再生料重量申报”前，用本系统核对称重账能否同时支撑各出货批的
再生料申报。Flask + SQLite + 网络流求解，全部重量按**整数公斤**处理。

## 一、业务规则与建模

1. 账套按炉记录外购**原生料**、外购**再生料**，按出货批记录实称重量，
   并记录余料从哪一炉转往哪一炉、转出多少（实称重量）。
2. 每炉**总进料 = 总出料**（CSV 导入时强制校验，不平衡直接拒收）。
3. 每个出货批最多一张**有效签单**（部分唯一索引保证；撤销记录留历史）。
4. 重核时已签重量照旧；归到各出货批和回炉余料的再生料重量可重新调整。
5. 每炉**再生料进出相等**；每笔出货、每笔转料的再生料重量均以实称重量为上限。
6. 页面给出一套满足全部有效签单的出货/回炉再生料重量；新签或换账无解时
   说明具体瓶颈原因；提交失败则回滚，原账、签单与既有核定结果全部保留。
7. **单批补签（优化项）**：
   - 现行账套中该批核定重量**已达申请下限**时，只登记签单、**跳过求解**，
     核定重量一行不改；
   - 否则以**签发前的核定值为基准**，使「各出货批 + 各笔转料」再生料重量
     改变量的**绝对值之和最小**，同时满足每炉守恒、实称上限与全部签单下限；
   - 只**写入重量有变的核定明细行**（未变动行的更新时间保持不变），成功后
     页面按批号/转料记录号列出每笔变动前后的公斤数与增减；
   - 无解或写入失败时整笔回滚，原签单与核定结果全部保留。

### 求解模型

整体核定使用带下界的整数网络流（`app/solver.py`，纯标准库实现的 Dinic）：

- `S → 炉`：容量为该炉外购再生料；
- `炉 → 出货批`：容量为批实称重量，**下界为有效签单下限**；
- `出货批 → T`：容量同为批实称重量；
- `炉 → 炉`：余料转料，容量为转料实称重量；
- `炉 → T`：富余再生料留存边（容量=该炉外购量），保证每炉再生料严格守恒，
  转来料必须继续排出，杜绝无外购再生料的炉凭空获得流量；
- 加 `T → S` 无穷边与超级源/汇，把带下界可行流转为最大流判定；
  可行后再跑一次 `S → T` 最大流，使出货承载尽量大。
- 容量均为整数，Dinic 保证得到整数解；无解时用残量网络最小割定位
  饱和的出货/转料通道与缺料炉，生成中文原因。

### 补签的最小变动求解（两阶段）

1. **阶段一·可行流**：先用上述带下界网络流求一版满足全部签单（含本次补签）、
   每炉守恒的整数可行流；不可行直接返回中文瓶颈原因，不写入。
2. **阶段二·残量最小费用调整**：在可行流的残量网络上，把每条可变边
   （炉→批、炉→炉转料）朝签发前基准调整的边际成本编码为 0/1 费用，
   反复取消负费用环，把可行流推向「离基准最近」的最优整数解。
   残量增广严格保持节点守恒，目标值即各批/各转料改变量绝对值之和。
3. 求解后再做守恒、实称上限、签单下界的终检，任一不满足按无解处理并回滚。

## 二、CSV 格式

UTF-8、首行表头，列固定为：

| 列 | 说明 |
|---|---|
| `record_type` | `furnace` / `batch` / `transfer` |
| `furnace` | 炉号（transfer 时为源炉） |
| `ref` | batch=出货批号；transfer=目标炉；furnace 留空 |
| `primary_kg` | 仅 furnace：外购原生料（留空按 0） |
| `recycled_kg` | 仅 furnace：外购再生料（留空按 0） |
| `weight_kg` | batch/transfer 的实称重量 |

示例见 `data/sample_ledger.csv`。

## 三、运行

### Docker Compose（交付方式）

```bash
docker compose up --build
# 打开 http://localhost:8000
```

SQLite 数据库存放在命名卷 `audit-data`（容器内 `/data/audit.db`），
容器重建数据不丢；生产环境请修改 `AUDIT_SECRET_KEY`。

### 本地直接运行

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
python wsgi.py            # 开发服务器，:8000
# 或
gunicorn --bind 0.0.0.0:8000 wsgi:app
```

## 四、页面操作

1. **上传 CSV**：首次直接导入；换账须勾选“替换当前账套”。导入即核定。
2. **核定结论**：展示可行方案或无解瓶颈；可随时“重新核定”。
3. **炉次账**：展示各炉进料/出料与平衡结果。
4. **出货批**：每行可补签（填正整数、不超过实称）或撤销签单，
   并显示该批核定再生料重量。补签时现行核定已达下限则只登记签单、跳过求解；
   否则按最小变动重核，页面顶部“本次补签的核定重量变动”按批号/转料记录号
   列出每笔变动前后的公斤数与增减，变动行高亮。
5. **余料转炉**：每笔转料的实称上限与核定再生料重量，补签变动同样高亮。
6. **签单台账**：有效/已撤销全部留痕。
7. **补签变动台账**：每次补签登记每一笔变动行（或一条“跳过求解”事件），
   含变动前后公斤数、增减与写入时间，供审核员逐笔核对。
8. **操作日志**：成功与失败（回滚）事件均记录。

## 六、目录结构

```
app/
  solver.py     带下界整数网络流（Dinic）、最小费用流与补签最小变动求解
  csvutil.py    CSV 解析与每炉物料平衡校验
  db.py         SQLite 建表、事务、签单/核定/行级明细/补签变动台账持久化
  web.py        Flask 路由（所有写操作单事务，先试算后提交）
  templates/    审核页（含补签变动高亮与变动台账）
  static/       样式
tests/          求解器、最小变动、CSV、端到端与补签流程测试
data/           示例 CSV
Dockerfile / docker-compose.yml / wsgi.py / requirements.txt
```

## 七、已有账套的兼容（无需重建数据库）

应用启动时自动执行幂等迁移：把旧版 `solution_batches` / `solution_transfers`
快照表中的核定结果填入新的行级明细表 `solution_batch_lines` /
`solution_transfer_lines`（`INSERT OR IGNORE`，可重复执行）。迁移后老账套
即可直接使用补签功能；历史签单与核定结果不丢失。
